# Контракт обмена: партнёрские обзоры → Routely

Сервис партнёра отдаёт обзоры блогеров, из которых наш ingest строит
характеристики отелей. Машиночитаемый образец ответа — `contract.sample.json`
(он же фикстура в `backend/tests/test_guides.py`, поэтому документ и код
не расходятся). Этот файл описывает не только «что прислать», но и
«что наш сервис с этим сделает».

## Направление обмена

- Партнёр — read-only источник: `GET /v1/guides?city=<slug>&updated_since=<iso8601>`.
- Забираем мы, офлайн-скриптом `scripts/ingest_guides.py` (как `fetch_data.py`).
- Ответ дополнительно сохраняется снапшотом в `data/guides/`, поэтому демо
  работает, когда сервис партнёра недоступен. Никаких запросов в рантайме.
- Инкремент: `updated_since` + `ETag`/`If-None-Match`. Удаление обзора
  передаётся как `status: "retracted"`, а не молчаливым исчезновением из выдачи.
- Адрес и токен партнёра — только через окружение (`GUIDES_API_URL`,
  `GUIDES_API_TOKEN`), в репозитории их нет.

## Как читать описание полей

Ниже каждое поле разобрано по схеме: **тип**, **обязательность**, **зачем**
и что именно делает наш сервис. Пометка «не читается» означает: значение
принимается и остаётся в снапшоте, но текущая версия ingest его не использует —
такие поля безопасно не присылать, и они не влияют на характеристики.

## Поля верхнего уровня

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `schema_version` | строка | да | Единственное поле (вместе с `partner.id`), отсутствие которого отклоняет **весь** пакет: по нему мы понимаем, каким разбором читать ответ |
| `generated_at` | ISO 8601 | нет | Момент формирования ответа; не читается, нужно для разбора инцидентов |
| `partner` | объект | да, нужен `id` | Кто источник: попадает в провенанс и в имя источника в БД |
| `region` | объект | нет | Регион выборки: из него берётся `bbox` для проверки координат |
| `guides` | массив | нет, но пустой = «обзоров нет» | Сами обзоры. Пустой массив валиден: это факт, а не ошибка |
| `paging` | объект | нет | Курсор для постраничной загрузки; не читается |

### `schema_version`

Строка, сейчас поддерживается только `"1.0"`. Любое другое значение —
полный отказ пакета с сообщением в отчёте ingest. Так мы можем менять
разбор полей, не гадая, какая версия перед нами.

### `generated_at`

Строка в ISO 8601 (`2026-02-10T09:00:00Z`). Не участвует в расчётах:
свежесть факта мы считаем по `published_at` обзора и по сроку жизни
характеристики (180 дней), а не по времени выгрузки.

### `partner`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `id` | строка-слаг | да | Идентификатор источника. Из него строится источник значения в БД: `blogger:<id>` |
| `name` | строка | нет | Отображаемое имя; при отсутствии подставляется `id`. Видно в провенансе значения |
| `license` | строка | да при `attribution_required` | Условия использования контента; попадает в провенанс и показывается рядом с фактом |
| `attribution_required` | bool | нет, по умолчанию `false` | Требование показывать автора и ссылку. Если `true`, а `license` пуст — ingest пишет предупреждение |
| `contact` | строка | нет | Контакт для вопросов по качеству данных; не читается |

`partner.id` — самое «дорогое» поле контракта: от него зависит, какие строки
в `hotel_features` обновятся. Менять идентификатор между синхронизациями
нельзя: для нас это выглядит как новый источник, старые значения останутся
висеть, а новый набор ляжет рядом.

### `region`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `bbox` | массив из 4 чисел | настоятельно рекомендуется | Границы выборки для проверки координат мест |
| `name`, `region`, `country` | строки | нет | Метаданные снапшота; не читаются |

`bbox` — `[min_lon, min_lat, max_lon, max_lat]`, порядок как в GeoJSON:
сначала долгота. Каждая точка проверяется на попадание внутрь; точка вне
рамки отклоняется как «перепутаны `lat`/`lon` или чужой город». Если `bbox`
не передан, проверка просто не выполняется — это хуже, потому что ошибка
координат попадёт в привязку к отелям.

### `guides[]`

Обзор (публикация) блогера. Один обзор может упоминать несколько мест.

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `id` | строка | да | Стабильный идентификатор обзора: ключ ретракции и дедупликации |
| `revision` | целое ≥ 1 | да | Версия обзора; растёт при правках. Нужен, чтобы отличать повторную выгрузку от новой версии |
| `status` | `"active"` / `"retracted"` | нет, по умолчанию `active` | Снятый обзор перестаёт подтверждать места |
| `updated_at` | ISO 8601 | да | Когда обзор последний раз менялся |
| `published_at` | ISO 8601 | да для `active` | Дата публикации: показывается рядом с цитатой, по ней оценивается свежесть |
| `url` | https-ссылка | да для `active` | Первоисточник. Показывается в карточке отеля и хранится в провенансе |
| `language` | BCP-47 | нет | Язык обзора; не читается (задел под мультиязычность) |
| `title` | строка | нет | Заголовок для интерфейса; не читается |
| `author` | объект | да | Кто автор: от этого зависит, считается ли подтверждение независимым |
| `media` | объект | нет | Обложка и тип публикации; не читается |
| `places` | массив | да, если обзор даёт факты | Места, о которых говорит обзор. Без них обзор валиден, но не подтверждает ничего |

`status: "retracted"` — отдельный случай. Для снятого обзора достаточно
`id`, `revision`, `updated_at`, `author.id`; `url`, `published_at` и `places`
не нужны, потому что он ничего не подтверждает. Идентификатор попадает
в список снятых, и все его свидетельства исключаются из расчёта — даже если
пришли в другом файле.

### `guides[].author`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `id` | строка | да, даже для `retracted` | Ключ независимости: два обзора одного автора — одно подтверждение, а не два |
| `name` | строка | нет | Подпись автора; при отсутствии подставляется `id`. Видна в карточке |
| `profile_url` | https-ссылка | нет | Профиль автора; не читается (нужен для атрибуции в будущем) |

Без стабильного `author.id` счётчик подтверждений надувается: перепечатка
одного текста разными площадками выглядела бы как консенсус нескольких
экспертов. Поэтому поле обязательное даже там, где не нужны ссылки.

### `guides[].media`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `kind` | `"video"` / `"photo"` / `"text"` | нет | Тип публикации; не читается |
| `cover_url` | https-ссылка | нет | Обложка; не читается |
| `duration_s` | целое | нет | Длительность видео; не читается |

Медиа не скачиваем и в репозиторий не кладём — только ссылки. Это прямое
следствие требований к сборке: тяжёлые артефакты в git не хранятся.

## Места: `guides[].places[]`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `key` | строка | да | Стабильный идентификатор места **между обзорами** — по нему склеиваются подтверждения |
| `name` | строка | нет | Название для интерфейса; при отсутствии подставляется `key` |
| `category` | строка | нет | Тип места (`viewpoint`, `beach`, `cafe`); не читается, нужно для отладки и будущих эмоций |
| `coordinates` | объект | да | Без координаты место не привязать к отелям |
| `osm` | объект | нет | Подтверждение, что место существует; повышает уверенность |
| `address` | строка | нет | Человекочитаемый адрес; не читается |
| `access` | объект | нет | Публичность, платность, режим работы; не читается |
| `emotions` | массив | да | Что именно обзор говорит про это место |

### `places[].key`

Строка, например `zelenogradsk-promenade-viewpoint-3`. Главное требование:
она должна быть **одинаковой в разных обзорах** для одного и того же места
и **разной** для разных мест внутри одного обзора.

Зачем: ключ — единица склейки. Три обзора про одну смотровую с одним `key`
дают одно место с тремя подтверждениями (и уверенность растёт), а три разных
ключа дадут три места по одному подтверждению каждое. При правке текста
обзора ключ менять нельзя — это тот же объект, а не новый.

Если место переименовали или оно переехало, `key` тоже меняется: для нас это
новый факт, старый истечёт по сроку жизни характеристики.

### `places[].coordinates`

```json
{ "coordinates": { "lat": 54.96011, "lon": 20.47302 } }
```

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `lat` | число | да | Широта, WGS84 |
| `lon` | число | да | Долгота, WGS84 |

Координата — вход для пешего маршрута от отеля до места; «рядом» у нас
измеряется метрами по улицам, а не по прямой. Если `region.bbox` передан,
точка обязана попасть внутрь рамки, иначе запись отклоняется. Обратите
внимание на порядок: `lat` — широта (≈54.96), `lon` — долгота (≈20.47);
перестановка не будет поймана, если `bbox` не задан.

### `places[].osm`

```json
{ "osm": { "type": "node", "id": 1234567890 } }
```

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `type` | `"node"` / `"way"` / `"relation"` | да, если объект передан | Тип объекта OSM |
| `id` | целое | да, если объект передан | Идентификатор объекта OSM |

Структура сейчас не валидируется: важен сам факт непустого объекта. Он даёт
два следствия — `osm_verified: true` в значении характеристики и прибавку
`+0.05` к уверенности. Если место в OSM не найдено, лучше не присылать
объект вовсе, чем присылать выдуманный идентификатор: проверить его мы
не можем, а доверие к данным строится на проверяемости.

### `places[].address` и `places[].access`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `address` | строка | нет | Подпись места; не читается |
| `access.public` | bool | нет | Место общедоступно; не читается |
| `access.free` | bool | нет | Бесплатно; не читается |
| `access.open_24h` | bool | нет | Круглосуточно; не читается |

Эти поля принимаются и остаются в снапшоте, но в расчёте не участвуют:
в карточке отеля мы показываем название, расстояние и время, а не режим
работы. Понадобятся, когда появится фильтр «доступно вечером».

## Эмоции: `places[].emotions[]`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `key` | строка | да | Какая эмоция; определяет, в какую характеристику отеля попадёт факт |
| `salience` | число 0..1 | да | Насколько место «про эту эмоцию» в глазах автора |
| `quote` | строка | да | Дословное подтверждение из обзора |
| `quote_locator` | объект | нет | Где именно в публикации эта цитата |
| `best_months` | массив целых 1..12 | нет | Когда эмоция работает; пусто — круглый год |
| `time_of_day` | массив строк | нет | Время суток (`evening`, `morning`) |

### `emotions[].key`

Ключ из таксономии партнёра. Сейчас поддерживается один:

| Ключ партнёра | Характеристика в нашем реестре |
| --- | --- |
| `sunset_spot` | `sunset_spot_nearby` |

Маппинг живёт у нас (`EMOTION_TO_FEATURE` в `backend/app/guides.py`), поэтому
словарь партнёра может меняться независимо от нашего реестра. Неизвестный
ключ — это ошибка записи (попадает в отчёт), а не тихий пропуск: молчание
скрыло бы, что партнёр начал отдавать новый тип эмоций.

Новая эмоция добавляется на нашей стороне в два шага: строка в маппинге
и блок характеристики в `features.yaml`.

### `emotions[].salience`

Число от 0 до 1 — вес этой эмоции в обзоре. Смысл: `0.9` — «ради заката сюда
и идут», `0.5` — «упомянул вскользь», `0.2` — «скорее фон». Значения вне
диапазона отклоняются. Строка вида `"0.8"` приводится к числу, но надёжнее
присылать число.

Как используется: по каждому месту берётся **лучший** отзыв каждого автора,
затем считается среднее по авторам — это `score` характеристики (0..1).
Так один восторженный обзор не тонет в десяти равнодушных упоминаниях,
но и не подменяет консенсус.

### `emotions[].quote`

Дословная цитата из обзора, непустая строка. Без неё запись отклоняется
целиком. Это главный защитный механизм контракта: факт, который нельзя
предъявить, у нас равен выдумке — ровно то, что ТЗ называет нерешением.

Цитата показывается в карточке отеля рядом с автором и ссылкой, поэтому она
должна читаться человеком и относиться именно к этому месту.

### `emotions[].quote_locator`

Необязательный объект свободной структуры: сохраняется в провенансе как есть
и нужен, чтобы цитату можно было проверить глазами. Структуру не валидируем,
но два вида значения реально проверяемы, поэтому рекомендуем только их.
В обзоре `quote_locator` содержит **один** элемент из массива ниже:

```json
[
  { "type": "video_timestamp", "value": "00:02:14" },
  { "type": "text_span", "start": 1840, "end": 1912 }
]
```

`video_timestamp` — таймкод в видео (`value` — строка `ЧЧ:ММ:СС`),
`text_span` — смещения символов в тексте публикации (`start` — от начала
текста, `end` — конец фрагмента). Для текстовой публикации лучше `text_span`,
для видео — таймкод. Произвольная структура вроде «примерно в середине»
проверке не поддаётся, поэтому она бесполезна: цитата без локатора ещё
принимается, но подтвердить её сможет только поиск по тексту.

### `emotions[].best_months` и `time_of_day`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `best_months` | массив целых | нет | Месяцы, когда эмоция работает: `[4,5,6,7,8,9]` |
| `time_of_day` | массив строк | нет | Время суток: `["evening"]` |

Месяцы вне диапазона 1..12 отбрасываются, пустой или отсутствующий список
означает «круглый год» (мы подставляем все 12) — иначе место выпадало бы
из выдачи из-за отсутствия поля, а не из-за факта. `time_of_day` сохраняется
как есть, без проверки по словарю.

Сейчас это контекст в карточке («месяцы: 4–9»); в поиске по датам поездки
поле станет фильтром.

## `paging`

| Поле | Тип | Обяз. | Зачем |
| --- | --- | --- | --- |
| `next_cursor` | строка или `null` | нет | Курсор следующей страницы; не читается |
| `total_guides` | целое | нет | Сколько обзоров всего; не читается |

Постраничная загрузка пока не используется: снапшот по одному региону
помещается в один ответ. Поля оставлены, чтобы включить пагинацию без
изменения контракта.

## Что происходит с данными дальше

1. **Проверка** (`app/guides.py`, `parse_batch`). Каждая запись проверяется
   отдельно; дефектная отклоняется с сообщением, остальные принимаются.
   Принцип «всё или ничего» здесь вреден: один битый обзор не должен
   блокировать обновление остальных.
2. **Склейка.** Обзоры группируются по `places[].key`, внутри места
   считаются независимые авторы по `author.id`. Два обзора одного автора —
   одно подтверждение.
3. **Маршрут.** Для каждой пары «отель ↔ место» считается пеший путь
   (тот же движок, что и «до моря»: дороги OSM, скорость, штраф за перепад).
   Пары дальше 1500 м по прямой не рассматриваются, места дольше 20 минут
   пешком не считаются «рядом».
4. **Выбор.** Из подходящих мест отеля берётся лучшее: сначала выше `score`,
   при равенстве — ближе по времени. Одно место на отель, без дублей.
5. **Запись.** Значение ложится в `hotel_features` источником
   `blogger:<partner.id>`, со сроком жизни 180 дней. Повторный ingest
   перезаписывает эту же строку, а не создаёт вторую.

Как выглядит записанное значение:

```json
{
  "score": 0.88,
  "nearest_minutes": 2.7,
  "distance_m": 216,
  "crosses_highway": false,
  "reviews": 2,
  "place_key": "zelenogradsk-promenade-viewpoint-3",
  "place_name": "Смотровая у третьего спуска",
  "osm_verified": true,
  "best_months": [3, 4, 5, 6, 7, 8, 9, 10],
  "time_of_day": ["evening"]
}
```

Уверенность считается у нас: `0.45 + 0.15 × min(авторов, 3) + 0.05`
за подтверждение OSM, потолок `0.95`. Один автор без OSM — `0.60`,
два автора с OSM — `0.80`, три и больше — `0.95`. Ниже `0.5` значение
не показывается: рядом с вычисленными характеристиками «наполовину
подтверждённое» выглядело бы так же уверенно, как проверенное.

Провенанс (в `raw_evidence`) хранит партнёра, лицензию, определение эмоции
и полный список свидетельств: `guide_id`, автор, ссылка, дата, цитата,
локатор, `salience`. Именно он показывается в карточке отеля: цитата, автор
и ссылка на первоисточник.

**Ретракция.** Если обзор приходит со `status: "retracted"`, все его
свидетельства исключаются из расчёта — в том числе пришедшие в другом файле.
Если у отеля не осталось подтверждений, строка удаляется, и характеристика
исчезает из карточки. Устаревание закрывает второй сценарий: место закрылось,
а обзор остался — через 180 дней значение истечёт без всякого сигнала
от партнёра.

## Правила отказа

Полный отказ пакета (ничего не применяется):

- ответ не является JSON-объектом;
- `schema_version` не поддерживается (сейчас только `1.0`);
- отсутствует `partner.id` — непонятно, чей это пакет.

Отклоняется отдельная запись, остальные принимаются:

| Причина | Что сообщает ingest |
| --- | --- |
| нет `guides[].id`, `revision`, `updated_at` или `author.id` | `обязательное поле «…» отсутствует` |
| у активного обзора нет `url` или `published_at` | `обязательное поле «…» отсутствует` |
| неизвестный `status` | `status: «…» не поддерживается` |
| нет `places[].key` | `обязательное поле «key» отсутствует` |
| нет или нечисловые `coordinates` | `нужны числовые lat и lon` |
| точка вне `region.bbox` | `точка вне региона` |
| неизвестный `emotions[].key` | `эмоция «…» неизвестна` |
| `salience` не число или вне 0..1 | `нужно число 0..1` |
| пустой `quote` | `без цитаты факт не принимается` |

Отдельно — предупреждение (пакет применяется): `attribution_required: true`
при пустом `partner.license`.

Молча пропускать нельзя: «партнёр ничего не прислал» и «партнёр прислал
битую запись» — разные состояния, и второе должно быть видно в отчёте.

## Чего в контракте намеренно нет

- **`confidence`.** Партнёр поставляет доказательства и вес (`salience`),
  уверенность считаем мы: число независимых авторов, подтверждение OSM,
  срок жизни. Присланная уверенность создала бы второй источник истины,
  и на вопрос «почему вы уверены» ответить было бы нечем.
- **Полных текстов обзоров.** Только цитаты: нам нужен минимальный фрагмент,
  который можно предъявить, а не копия чужой публикации.
- **Медиафайлов.** Только ссылки — тяжёлые артефакты не хранятся в git
  и не скачиваются при сборке.
- **Персональных данных авторов** сверх имени и публичного профиля.
- **Рейтингов, лайков, просмотров.** Они не отличают «место действительно
  про закат» от «обзор популярный».

## Юридическое

`partner.license` и `author` обязательны к показу в интерфейсе рядом
с фактом: обзор остаётся чужой публикацией, мы показываем атрибуцию
и ссылку на первоисточник. Ограничения лицензии (в том числе запрет
на производные данные) должен сообщать партнёр — от этого зависит,
можно ли использовать обзор в ранжировании.
