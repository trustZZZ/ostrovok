# Routely × Островок — агентный подбор отелей по характеристикам, которых нет в карточке (трек «О!дин шаг до идеального отеля»)

Система собирает характеристики отелей, которых нет в описаниях: вид на закат над морем, уровень шума, реальный пеший путь до пляжа. Гео-характеристики вычисляются по рельефу и 3D-зданиям OSM, недостающее агент выясняет у отельера. У каждого значения хранится источник, уверенность и доказательства, а поиск идёт по запросу на естественном языке.

## Быстрый старт

```bash
git clone <URL репозитория>
cd <repo>
cp .env.example .env      # опционально: без ключа LLM работает в мок-режиме
docker compose up --build
# открыть http://localhost:8080
```

Docker Desktop (или Docker Engine) должен быть запущен. Первая сборка занимает 5–8 минут (GDAL и гео-библиотеки), повторный запуск — меньше минуты.

Проверка готовности: `curl http://localhost:8080/health` →

```json
{ "status": "ok", "service": "routely-ostrovok" }
```

## Зависимости и переменные окружения

Рекомендуемые ресурсы:

- 2 CPU cores
- 4 GB RAM
- 5 GB свободного диска

Сервисы:

- **db** — PostgreSQL 16 + PostGIS 3.4 (образ `postgis/postgis:16-3.4`), наружу не публикуется

### Про ключ LLM

Ключ **не обязателен**: при `USE_MOCK_LLM=1` (значение по умолчанию) система работает полностью, LLM-шаги отдают детерминированные заглушки. Если ключ указан и `USE_MOCK_LLM=0`, включаются реальные вызовы LLM (парсинг запроса, формулировка вопросов отельеру, разбор его ответов). Ключ читается из `LLM_API_KEY` или `OPENAI_API_KEY` — достаточно одной переменной.

## Данные и сидирование

Демо-данные уже лежат в `data/` (суммарно ~6 МБ) — при старте ничего скачивать не нужно:

| Файл                    | Содержимое                                                        | Объём   |
| ----------------------- | ----------------------------------------------------------------- | ------- |
| `hotels.geojson`        | 8 реальных гостиниц OSM; этажность и адрес — из PBF               | 4 КБ    |
| `dem.tif`               | SRTM 3 arcsec (≈90 м) по области, 1620×1800                       | 668 КБ  |
| `buildings.gpkg`        | 5474 здания OSM в радиусе 2.2 км от отелей; у 2886 известна этажность | 3.1 МБ  |
| `noise_sources.geojson` | 4440 объектов: дороги, железные дороги, бары, кафе                | 1.4 МБ  |
| `beaches.geojson`       | 1022 объекта воды, из них 18 пляжей (используются для «до моря»)   | 470 КБ  |
| `seed.sql`              | сид для PostgreSQL (таблицы создаёт SQLAlchemy)                   | 394 Б  |

Отели в БД синхронизируются при каждом старте backend: новые добавляются, существующие (по `osm_id`) обновляются, а те, которых больше нет в файле, удаляются вместе с характеристиками — демо-набор всегда совпадает с источником.

Пересобрать данные из первоисточников можно одной командой — локальный Python не нужен, всё считается внутри backend-образа:

```bash
make data          # Geofabrik (экстракт области: shapefile + PBF) + SRTM
# ≈3–6 минут, требуется ~85 МБ загрузки
curl http://localhost:8080/api/hotels/enrich-all -X POST   # собрать характеристики
```

Если нужны только высоты зданий (после правок в PBF-разборе), пересобирается один слой — около минуты, без shapefile и DEM:

```bash
make data-buildings   # только buildings.gpkg из OSM PBF
```

Сбор устроен так: официальный экстракт области (Geofabrik) обрезается до окрестностей отелей, рельеф берётся из SRTM (`elevation-tiles-prod`). Публичный Overpass API для этого не используется: он отдаёт 429/502 под нагрузкой, а часть зеркал (например, `overpass.osm.ch`) — региональные экстракты и молча возвращают пустоту.

Здания читаются из PBF того же экстракта (`kaliningrad-latest.osm.pbf`, разбор через `pyosmium`): только там есть теги `building:levels` и `height`, которых нет в shapefile. Замкнутые way и отношения-мультиполигоны собираются в один слой, высота берётся из `building:levels` (× 3 м) либо из `height`.

Отели в `data/hotels.geojson` — тоже настоящие объекты OSM: `osm_id`, названия и адреса взяты из карты, а этажность перечитывается из того же PBF по `osm_id` при каждой сборке (`floors_source: osm_pbf`). Точка отеля — `representative_point` контура его здания, поэтому лучи заката и путь до моря считаются изнутри дома, а не из угла way. Если PBF недоступен, остаётся снимок этажности из списка `HOTELS`, и источник помечается как `snapshot`.

**Ограничение точности:** теги высоты в OSM заполнены не у всех зданий — в демо-слое этажность известна у 2886 из 5474 объектов (53%), остальным инструмент подставляет 9 м. Поэтому в `raw_evidence` пишется `buildings_with_known_height` и `building_height_source`: по ним видно, посчитан вид по реальной застройке или по константе. Пересобрать отели с этажностью отдельно: `make data-hotels`.

Таблицы в БД создаются автоматически при старте backend (`Base.metadata.create_all` + идемпотентные `ALTER TABLE` для новых колонок).

## Архитектура

```
FRONTEND (React + nginx :8080)
  Home │ Search │ Hotel │ Hotelier │ Compare
  MapLibre GL (карта + лучи заката)
        │  REST /api, nginx проксирует в backend
        ▼
BACKEND (FastAPI :8000)

  features.yaml  ── реестр характеристик (данные, не код)
        │
        ▼
  plan → collect → save → conflicts → ask → wait → parse → finalize
   │        │                 │                          │
   │        │                 └─ вопрос отельеру          └─ запись в БД
   │        └─ инструменты: sunset_view, noise_score,
   │                        walk_to_sea, climate
   └─ решает, какие инструменты нужны для каждой характеристики
      и фиксирует обоснование в evidence.tool_selection

  PostgreSQL + PostGIS
  hotels │ hotel_features │ hotelier_questions │ routes
```

Ключевое отличие от «просто пайплайна»: состав шагов и инструментов задаётся реестром `features.yaml`. Новая характеристика добавляется блоком в YAML, а не правкой графа.

### Модель достоверности

Каждая характеристика хранится в `hotel_features` со служебными полями:

- `source` — откуда значение (гео-вычисление, отельер, открытые данные)
- `confidence` — уверенность 0..1
- `raw_evidence` — доказательства: параметры вычисления, промежуточные значения
- `computed_at`, `expires_at` — когда получено и когда считается устаревшим

## Ключевая характеристика: «вид на закат над морем»

Алгоритм raycasting по DEM и 3D-зданиям OSM:

1. Азимут заката через `pysolar` — для каждого проверяемого месяца отдельно
2. Сверка со стороной фасада: если главный фасад смотрит больше чем на 90° от
   заката, окна выходят в другую сторону и месяц не засчитывается
3. Луч от точки обзора (отель + высота этажа × 3 м) в сторону заката до 10 км
4. Сэмплирование DEM вдоль луча — проверка перекрытия рельефом
5. Фильтрация зданий OSM с высотой — проверка перекрытия застройкой; здание самого отеля исключается, иначе оно затеняло бы вид из собственного окна
6. Перебор этажей — минимальный этаж с открытым видом
7. Результат: `{visible, from_floor, months, confidence, evidence}`

Сторона фасада оценивается по направлению на ближайшую улицу: OSM не хранит
сторону входа, а вход в городской отель почти всегда с улицы. Это оценка, а не
факт, поэтому `evidence.facade_source` фиксирует способ получения, а
`evidence.block_reason` различает две причины отказа: `facade_facing_away`
(окна не туда) и `obstructed` (вид загорожен). От причины зависят разные
действия — номер на другую сторону или этаж повыше.

## Метрики качества

Замер запускается одной командой при поднятом стеке:

```bash
make eval    # docker compose --profile tools run --rm seed python /scripts/evaluate.py
```

Фактический прогон на демо-наборе (8 отелей, Калининградская область):

| Характеристика   | Покрытие   | Проверка                                                              |
| ---------------- | ---------- | --------------------------------------------------------------------- |
| `sunset_view`    | 8/8 (100%) | 3/8 совпадений с baseline; все 5 расхождений объяснены; accuracy на разметке не измерена |
| `noise_score`    | 7/8 (88%)  | ранговая корреляция +0.96 (n=7) с плотностью источников                |
| `walk_to_sea`    | 4/8 (50%)  | MAE 2.8 мин к независимой оценке «по прямой × 1.3» (n=4)               |
| `climate_summer` | 8/8 (100%) | данные Open-Meteo, проверяются на стороне источника                    |

Что эти числа означают честно:

- **Покрытие** измеряется всегда и разметки не требует. Четыре отеля с
  `walk_to_sea` — прибрежные; у остальных пляжа в радиусе нет, поэтому
  значения нет, и придумывать его мы не стали.
- **MAE 2.8 мин** — отклонение от *baseline*, а не от истины. Baseline
  считается независимым способом (прямое расстояние до пляжа × коэффициент
  извилистости), поэтому метрика ловит расхождение в разы, но не точность
  до минуты.
- **3/8 для `sunset_view`** — тоже согласие с baseline, а не accuracy.
  Baseline проверяет по одному DEM, без зданий, без перебора этажей и без
  учёта стороны фасада: открыт ли горизонт на западе с верхнего этажа.
  Поэтому расхождения ожидаемы, и отчёт делит их на объяснённые: застройкой
  на луче (2 отеля) и ориентацией окон (3 отеля — главный фасад смотрит на
  юг или восток). Необъяснённых расхождений нет, и, что важнее, нет
  ложноположительных: инструмент ни разу не сказал «виден», когда рельеф
  закрыт. Именно этот класс ошибки самый опасный — гость приедет за закатом,
  которого нет.
- **+0.96 для `noise_score`** — ранговая корреляция Спирмена с простой
  плотностью источников шума в радиусе 400 м, без весов и затухания. Она
  проверяет порядок отелей, а не абсолютный балл: веса по типам и
  расстоянию не переставляют отели местами.
- **Accuracy `sunset_view` и `noise_score` не измерена.** Для неё нужна
  ручная разметка: `data/ground_truth.csv` содержит шаблон с колонками
  `sunset_visible` (0/1), `noise_level` (low/medium/high), `walk_minutes_ref`.
  Пустые поля не считаются — подставлять вместо них наши же значения значило
  бы измерять систему самой собой. Заполненные строки `make eval` подхватит
  и выведет accuracy/MAE отдельным блоком.

## Кросс-платформенность

- Все зависимости работают внутри Docker; ручных доустановок не требуется
- Контейнеры собраны по multi-stage, без root и без dev-инструментов в рантайме
- Версии базовых образов зафиксированы: `postgis/postgis:16-3.4`, `python:3.11.10-slim-bookworm`, `node:20.18.1-alpine`, `nginxinc/nginx-unprivileged:1.27-alpine`
- Платформа задана явно: `platform: linux/amd64` у всех сервисов, включая `db` и образ с GDAL, поэтому на Apple Silicon собирается тот же образ, что и на amd64
- Конфигурация читается из `.env` через `env_file` у `db` и `backend`; файл не обязателен — без него действуют значения по умолчанию из `docker-compose.yml`
- Если в уже открытом терминале `make` не находится — выполните `source ~/.bashrc` или перезапустите терминал
