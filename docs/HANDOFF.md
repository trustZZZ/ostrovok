## 1. Правила работы с этим репозиторием

1. **Ничего не коммитить без явной просьбы.** Пользователь коммитит сам.
2. **Не подгонять эталон под расчёт.** `data/ground_truth.csv` заполняется по внешним
   источникам (панорамы, отзывы), а не значениями из нашей же системы. Иначе метрика
   измеряет саму себя.
3. **Не выдумывать данные.** Если характеристики нет — писать «нет данных» с
   `confidence: 0`. Отсутствие значения честнее правдоподобной догадки: весь смысл
   трека в достоверности.
4. **Секреты.** В локальном `.env` лежит реальный ключ LLM. Он в `.gitignore` и в git не
   попадает. Не выводить его в чат, не вставлять в файлы, не коммитить. Ключ светился в
   выводе `docker compose config` — пользователю рекомендовано его перевыпустить.
5. Перед началом работы: `git status` — там могут быть незакоммиченные правки.

## 2. Что за проект и в рамках чего он сделан

Прототип агентной системы для хакатона Островка, трек
**«О!дин шаг до идеального отеля»**.

Задача трека: собирать характеристики отелей и номеров, которых нет в карточках
(вид на закат, шум, реальная доступность моря), систематизировать их с указанием
источника, уверенности и срока актуальности, и давать по ним поиск на естественном
языке. Ключевое требование: характеристика должна быть **достоверно получена**, а не
угадана языковой моделью.

Наше решение: геофизика вместо догадок. Вид на закат считается raycast-ом по рельефу
(SRTM) и высотам зданий (OSM), шум — по расстоянию до дорог, железной дороги и ночных
заведений, время до пляжа — по реальному пешему графу OSM. То, что нельзя вычислить
(шумоизоляция, номера на запад, питомцы), агент спрашивает у отельера.

Регион: Калининградская область (Калининград + Зеленоградск). Демо-набор — 12 реальных
отелей: Crystal House, Калининград, Кайзерхоф, Парадокс, Royal Lions, Королева Луиза,
Sambia, Замок «Нессельбек» (8 исходных) и Априори, Кандинский, Принцесса Элиза,
Ренессанс — первая линия Зеленоградска, 1.5–4 минуты пешком до пляжа.

## 3. Быстрый старт

```bash
cp .env.example .env          # без ключа LLM работает детерминированный разбор пожеланий
docker compose up --build     # ~5–8 минут на первую сборку
# открыть http://localhost:8080
```

Проверка живости: `http://localhost:8080/health` → `{"status":"ok", ...}`.

Полезные команды (`make`-цели):

| Команда | Что делает |
| --- | --- |
| `make up` | поднять стек (`docker compose up --build`) |
| `make down` | остановить контейнеры |
| `make data` | пересобрать демо-данные в `./data` (Geofabrik + SRTM, ~55 МБ загрузки) |
| `make data-buildings` | только здания из OSM PBF (реальные `building:levels`), ~1 мин |
| `make data-hotels` | только отели из PBF (этажность, адреса); после — `restart backend` |
| `make eval` | замер качества характеристик (стек должен быть поднят) |
| `make demo` | демо целиком: сбор → ответы отельера → поиск (стек должен быть поднят) |
| `make test` | pytest в отдельном dev-образе |
| `make clean` | снести контейнеры вместе с томом БД |

**Демо-данные уже лежат в `data/`** — при первом запуске ничего скачивать не нужно.
`make data` нужен только для пересборки.

## 4. Архитектура и поток данных

```
FRONTEND (React + Vite, nginx, :8080)
  Home │ Search │ Hotel │ Hotelier │ Compare
        │ REST /api
        ▼
BACKEND (FastAPI, :8000)
  features.yaml (реестр характеристик — единственный источник списка фич)
        │
        ▼
  plan → collect → save → conflicts → ask → wait → parse → finalize
   │        │                │                          │
   │        │                └─ вопрос отельеру         └─ запись в hotel_features
   │        └─ инструменты: sunset_view, noise_score, walk_to_sea, climate_summer
   └─ выбирает инструменты под характеристику, обоснование в raw_evidence
  PostgreSQL + PostGIS: hotels │ hotel_features │ hotelier_questions │ routes
```

Слои данных:

1. **Сбор (offline, `scripts/fetch_data.py`)** — Geofabrik `kaliningrad-latest` (PBF для
   зданий с этажностью, free-shapefile для дорог/POI/воды) + SRTM 3 arcsec (`skadi`).
   Результат: `data/buildings.gpkg`, `data/noise_sources.geojson`, `data/beaches.geojson`,
   `data/hotels.geojson`, `data/dem.tif`.
2. **Вычисление (online, `backend/app/tools/`)** — чистые функции: вход — координаты и
   слой, выход — значение + `confidence` + `evidence`.
3. **Оркестрация (LangGraph, `backend/app/agents/graph.py`)** — решает, что считать, что
   спросить, и что записать.
4. **Хранение** — `hotel_features` хранит историю версий: одна строка на пару
   (отель, характеристика, источник). Провенанс: `source`, `confidence`, `raw_evidence`,
   `computed_at`, `expires_at`, `disputed`, `disputed_with`.
5. **Выдача** — `search_engine.py` разбирает пожелание, ранжирует по фактическим строкам
   БД и собирает объяснение из `evidence`. UI только рендерит.

Ключевой принцип: **фича — это не строка отеля, а знание с провенансом.** Поэтому система
может честно сказать «нет данных» и умеет замечать противоречия между источниками.

## 6. Реестр характеристик

`backend/app/features.yaml` — **единственное место**, где перечислены характеристики.
Граф и поиск читают его при старте и не содержат списка фич в коде. Добавление
характеристики = новый блок в YAML (и, опционально, инструмент в `collectors.py`).

| Ключ | Уровень | Инструмент | Источник | TTL | Смысл в поиске |
| --- | --- | --- | --- | --- | --- |
| `sunset_view` | отель | `sunset_view` | SRTM + OSM buildings | 365 д | закат виден (`==`) |
| `noise_score` | отель | `noise_score` | OSM roads/rail/POI | 180 д | шум ≤ порога |
| `walk_to_sea` | отель | `walk_to_sea` | OSM дороги + вода | 365 д | минут до пляжа ≤ порога |
| `climate_summer` | отель | `climate_summer` | Open-Meteo ERA5 | 30 д | июльская температура ≥ порога |
| `pet_friendly` | отель | — (только отельер) | отельер | 180 д | `==` |
| `room_west_windows` | номер | — (только отельер) | отельер | 180 д | `==` |
| `room_silence` | номер | — (только отельер) | отельер | 180 д | `==` |
| `room_balcony` | номер | — (только отельер) | отельер | 180 д | `==` |

Поля блока YAML и зачем они:

- `tools` — имена из `collectors.TOOL_REGISTRY`. Пусто = характеристику знает только
  отельер, агент сразу формулирует вопрос.
- `question` — текст вопроса отельеру. Формулируется один раз в реестре, а не в коде.
- `value_field` — какое поле значения сравнивать при поиске (значение почти всегда
  словарь, а сравнивать нужно одно число или флаг).
- `search.op` — как трактовать пожелание: `==` (точное), `<=` (меньше — лучше),
  `>=` (больше — лучше).
- `search.min` / `search.max` — допустимые границы порога. **Обязательны для числовых
  фич**: LLM на запрос «тихий номер» возвращала `noise_score: 0`, что отсекало все
  отели; зажим возвращает осмысленные 10–30.
- `ttl_days` — через сколько значение считается устаревшим (попадает в `/hotels/stale`).
- `min_confidence` — ниже этого порога значение не сохраняется как факт, а уходит
  в вопрос отельеру.

## 7. Модель достоверности

Каждая характеристика — строка `hotel_features` с провенансом:

| Поле | Смысл |
| --- | --- |
| `feature_key` | ключ из реестра |
| `value` | JSONB: структурированное значение (не готовая строка для UI) |
| `source` | **каноническое** имя источника (`SRTM+OSM`, `OSM`, `OSM roads + bathing water`, `Open-Meteo`, `hotelier`) |
| `confidence` | 0..1, насколько источник уверен |
| `raw_evidence` | методика, промежуточные числа, причина отказа, `tool_selection` |
| `computed_at` / `expires_at` | когда получено / когда перепроверить |
| `disputed` / `disputed_with` | расхождение с другим источником и детали |

Правила, которые нельзя ломать:

1. **Одна строка на (отель, характеристика, источник).** `upsert_feature` удаляет прежнюю
   строку того же источника перед вставкой. Из-за этого имя источника обязано быть
   одинаковым при успехе и при ошибке — иначе копятся дубли, которые выглядят как
   расхождение источников (см. грабли №5).
2. **Технический сбой не затирает данные.** Если инструмент упал по сети, а прошлое
   значение ещё не просрочено, оно сохраняется (`_should_persist`). Осознанное
   «нет данных» (нет пляжа в радиусе) пишется как факт.
3. **Противоречия.** При записи сравниваются значения других источников по
   `value_field`; при расхождении обе строки получают `disputed` и `disputed_with`.
4. **Кто побеждает.** `feature_registry.resolve_rows` выбирает строку по `authoritative`:
   для измеримых характеристик (есть `tools`) — геоданные, для субъективных (номерные,
   питомцы) — отельер. Поиск обязан использовать `resolve_rows`, а не свой
   `max(confidence)`.
5. **Разбор противоречия** — `POST /api/hotelier/{hotel_id}/resolve/{feature_key}`:
   отельер подтверждает значение, оно пишется с `source=hotelier`, `confidence 0.95`,
   и `disputed` пересчитывается.

## 10. Метрики: фактические цифры

Последний прогон `make eval` (12 отелей, 96 строк характеристик):

| Характеристика | Покрытие | Проверка |
| --- | --- | --- |
| `sunset_view` | 12/12 (100%) | 3/12 совпадений с baseline (25%); из 9 расхождений 3 объяснены застройкой, 6 — стороной фасада |
| `noise_score` | 11/12 (92%) | ранговая корреляция +0.91 (n=11) с плотностью источников |
| `walk_to_sea` | 8/12 (67%) | MAE 4.8 мин к оценке «по прямой × 1.3», смещение −3.8 мин (n=8) |
| `climate_summer` | 12/12 (100%) | данные Open-Meteo, проверяются на стороне источника |

Как это читать (и как отвечать жюри):

- **Покрытие ≠ точность.** 12/12 у заката означает «значение есть у всех», в том числе
  `visible: false`. Восемь отелей с `walk_to_sea` — прибрежные, у остальных пляжа
  в радиусе нет, и значение не выдумывается.
- **baseline — не истина.** Для заката baseline проверяет только рельеф, без зданий,
  без этажей и без фасада. Поэтому 5 расхождений ожидаемы: 2 объясняются застройкой
  на луче, 3 — ориентацией окон. **Ложноположительных нет** — инструмент ни разу не
  сказал «виден», когда рельеф закрыт. Это самый опасный класс ошибки.

  по внешним источникам: `sunset_visible` (0/1), `sunset_from_floor`, `noise_level`
  (low/medium/high), `walk_minutes_ref`. Пустые поля не считаются.
- Ранее в README и на главной странице фигурировали выдуманные «88% точности» — убраны.
  На главной теперь «Ложных «виден закат» — 0».

Отдельно про окружение:

- **PowerShell 5.1 портит UTF-8.** `Invoke-RestMethod` в выводе показывает кракозябры,
  а JSON в БД чистый. Не «исправляй» данные из-за этого — проверяй через браузер или
  байты: `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`, тело запроса
  отправляй как `UTF8.GetBytes(...)`.
- **`docker compose config` печатает реальные значения `.env`**, включая ключ. Не выводить
  в чат и не вставлять в файлы.
- **Uvicorn работает без `--reload`.** После правки Python нужен
  `docker compose restart backend`. Код приходит через bind-mount `./backend:/app`.
- **Фронтенд собирается заново** только через `docker compose build frontend`.
- `docker compose ... 2>&1` в PowerShell может падать с `NativeCommandError` на прогрессе
  docker — использовать `cmd /c "docker compose build frontend 2>&1"`.

## 14. Рецепты проверки (проверять фактом, а не на глаз)

```bash
# 1. Поднять/перезапустить
docker compose up -d --build
docker compose restart backend        # после правок Python

# 2. Здоровье
curl -s http://localhost:8080/health

# 3. Собрать характеристики для всех отелей (~2 минуты, фоновые задачи)
curl -s -X POST http://localhost:8080/api/hotels/enrich-all

# 4. Посмотреть, что получилось
curl -s http://localhost:8080/api/hotels | head -c 2000
curl -s http://localhost:8080/api/hotels/9/features

# 5. Поиск
curl -s -X POST http://localhost:8080/api/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"тихий номер с видом на закат недалеко от моря","limit":5}'

# 6. Замер
make eval
```

Что смотреть в ответах:

- `features[].confidence`, `source`, `raw_evidence.block_reason` — обоснование;
- `explanation` в поиске — должно ссылаться на реальные значения, включая «нет данных»;
- `stale` / `disputed` — флаги достоверности.

Изменения в UI проверять в браузере на `http://localhost:8080/#/hotel/{id}` —
**с решёткой**, иначе откроется главная.

## 15. Переменные окружения и ресурсы

Все значения по умолчанию — локальные демо, не для продакшена.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |

`frontend` (nginx-unprivileged :8080), плюс профиль `tools` — `seed` (сбор данных,
