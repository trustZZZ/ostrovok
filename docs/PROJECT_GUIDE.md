Документ описывает **то, что реально реализовано в коде**, а не замысел. Каждое
утверждение проверяемо: указан файл, а числа взяты из констант проекта.

Рассчитан на три задачи:

1. **Защита перед жюри.** Разделы 1–3 и 15 отвечают «что и зачем», раздел 17 —
   «что не работает», чтобы не обещать лишнего.
2. **Передача другому разработчику.** Разделы 4–13 — как устроено внутри.
3. **Собственное понимание.** Раздел 6 (реестр), 7 (граф), 8 (достоверность) и
   9 (алгоритмы) объясняют, почему приняты именно такие решения.

Термины и материалы для изучения — в `docs/GLOSSARY.md`. Готовые ответы на
вопросы жюри — в `docs/DEFENSE_QA.md`.

## 1. Что это за продукт

Трек: «О!дин шаг до идеального отеля» (Островок).

Проблема из ТЗ: стандартные фильтры отвечают про звёзды, завтрак и Wi-Fi, а
«виден ли закат из окна», «насколько шумно под окнами», «сколько реально идти до
моря» — гость выясняет сам по отзывам, фото и панорамам. На это уходят часы, и
часть броней отменяется уже на месте.

Что делает прототип:

1. **Собирает характеристики, которых нет в карточке отеля** — из открытых
   геоданных (рельеф, здания, дороги) и из ответов отельера.
2. **Хранит каждое значение с провенансом** — источник, уверенность, дата,
   доказательства, срок актуальности.
3. **Ищет по свободному описанию** — «тихий номер с видом на закат над морем,
   5 минут до пляжа» → структурированные ограничения → ранжирование по фактам.
4. **Показывает, чего не хватает** — если данных нет, агент формулирует вопрос
   отельеру и раскладывает свободный ответ по полям.

Демо-регион — Калининградская область: 12 реальных гостиниц OSM (3 в
Калининграде, 8 в Зеленоградске, 1 в Орловке). Один регион выбран сознательно:
лучше глубоко проработать его, чем поверхностно покрыть несколько (это и
рекомендация ТЗ).

Характеристик в реестре девять.

Характеристики в реестре (`backend/app/features.yaml`):

| Ключ | Что означает | Как получаем |
| --- | --- | --- |
| `sunset_view` | виден ли закат над морем и с какого этажа | raycasting по DEM + 3D-зданиям OSM |
| `noise_score` | шум 0–100 | веса по типам источников OSM и расстоянию |
| `walk_to_sea` | минуты пешком до пляжа | кратчайший путь по графу дорог + рельеф |
| `climate_summer` | средний июльский максимум | архив Open-Meteo (ERA5) |
| `pet_friendly` | пускают ли с животными | ответ отельера |
| `room_west_windows`, `room_silence`, `room_balcony` | характеристики номеров | ответ отельера |
| `sunset_spot_nearby` | закатная точка в пешей доступности | партнёрские обзоры + пеший маршрут |

## 2. Пользовательские сценарии

**Гость.** Вводит свободный текст на `/search`. Бэкенд разбирает его в
ограничения по характеристикам, ранжирует отели по фактическим значениям из БД и
возвращает объяснение по каждому: что совпало, что нет, с какой уверенностью и
из какого источника. На карте — лучи заката от отелей (оранжевый — виден,
серый — нет).

**Отельер.** В `/hotelier` видит вопросы агента и историю ответов. Отвечает
свободным текстом — значение записывается отдельным источником `hotelier` с
разобранным значением и уверенностью. Там же разбирает расхождения источников и
запускает перепроверку устаревших значений.

**Система (агент).** По `POST /api/hotels/{id}/enrich` проходит граф:
планирует характеристики → запускает инструменты → сохраняет → ищет противоречия
→ при неуверенности задаёт вопрос и ждёт ответа → финализирует.

## 3. Запуск и что происходит при старте

```bash
cp .env.example .env      # опционально: без ключа LLM работает мок-режим
docker compose up --build
# http://localhost:8080
```

При старте backend (`backend/app/main.py`, `lifespan`):

1. `Base.metadata.create_all` — создаёт таблицы, если их нет.
2. `ensure_schema` — идемпотентные `ALTER TABLE` для колонок, которые `create_all`
   не добавляет в существующую таблицу, плюс нормализация источника и удаление
   дублей «одна строка на источник».
3. `seed_hotels` — синхронизирует отели из `data/hotels.geojson` по `osm_id`:
   новые добавляет, существующие обновляет, отсутствующие в файле **удаляет
   вместе с характеристиками**. Файл — источник истины демо-набора.
4. Подключается Postgres-checkpointer для графа; при любой ошибке остаётся
   `MemorySaver` и приложение всё равно стартует.

Данные для работы уже лежат в `data/` (~6 МБ): при старте ничего не скачивается.
Пересборка из первоисточников — `make data` (Geofabrik + SRTM, 3–6 минут).

Проверка готовности: `curl http://localhost:8080/health` →
`{"status":"ok","service":"routely-ostrovok"}`.

## 4. Архитектура и поток данных

```
FRONTEND (React + Vite → nginx-unprivileged :8080)
  Home │ Search │ Hotel │ Hotelier │ Compare
  MapLibre GL (тайлы OSM + лучи заката)
        │ REST /api, nginx проксирует в backend:8000
        ▼
BACKEND (FastAPI :8000)
  routers: search │ hotels │ hotelier │ routes │ agent (SSE)
  agents/graph.py — LangGraph: plan → collect → save → conflicts → ask → wait → parse → finalize
  tools/: sunset_view │ noise_score │ walk_to_sea │ facade
        │
        ▼
PostgreSQL 16 + PostGIS 3.4
  hotels │ hotel_features │ hotelier_questions │ routes
```

Компоненты и их ответственность:

| Слой | Файл | Что делает |
| --- | --- | --- |
| Реестр | `app/features.yaml`, `app/feature_registry.py` | какие характеристики существуют, чем собираются, какой у них порог доверия и как трактовать пожелание |
| Инструменты | `app/collectors.py`, `app/tools/*` | считают значение и возвращают его вместе с провенансом |
| Агент | `app/agents/graph.py` | решает, что запускать, когда спрашивать отельера, что записывать |
| Хранилище | `app/models.py`, `app/seed.py` | одна строка на (отель, характеристика, источник), пересчёт `disputed` |
| Поиск | `app/search_engine.py` | разбор пожелания, выбор значения среди источников, ранжирование, объяснение |
| API | `app/routers/*`, `app/main.py` | REST + SSE |
| UI | `src/*` | карточки, карта, кабинет, сравнение |

Почему так, а не «один скрипт»:

- **Реестр вместо кода.** Граф и поиск не содержат списка характеристик: они
  читают YAML. Новая характеристика — блок в YAML, а не правка Python. Это
  прямое требование ТЗ про расширяемость.
- **Сбор отделён от чтения.** Граф пишет в БД, поиск читает из БД. Поиск не
  запускает вычисления на каждый запрос: дорогие расчёты (raycasting, маршруты)
  выполняются один раз при сборе.
- **Провенанс рядом со значением.** Не отдельный лог, а поля той же строки:
  иначе объяснение в выдаче пришлось бы собирать из логов.

## 5. Данные: что именно используется и откуда

Все слои собираются скриптом `scripts/fetch_data.py` и лежат в `data/`.

| Файл | Содержимое | Объём | Источник |
| --- | --- | --- | --- |
| `hotels.geojson` | 12 гостиниц: `osm_id`, имя, адрес, этажность, точка | 5.4 КБ | список в скрипте + теги OSM PBF |
| `dem.tif` | рельеф, 1620×1800 px, ≈90 м/пиксель | 668 КБ | SRTM 3 arcsec (`elevation-tiles-prod`) |
| `buildings.gpkg` | 5474 контура зданий в радиусе 2.2 км; у 2886 (53%) известна этажность | 3.1 МБ | Geofabrik PBF (`pyosmium`) |
| `noise_sources.geojson` | 4440 объектов: дороги, железная дорога, бары, кафе | 1.4 МБ | Geofabrik shapefile |
| `beaches.geojson` | 1022 объекта воды, из них 18 пляжей | 470 КБ | Geofabrik shapefile |
| `guides/local-guides.json` | 2 места, 3 обзора партнёрского корпуса | 9.6 КБ | подготовлено по контракту |
| `seed.sql` | сид для initdb | 394 Б | — |

Геометрия и координаты:

- Система координат — **WGS84 (EPSG:4326)**, координаты в порядке `lon, lat`
  (как в GeoJSON). В коде это критично: `Point(lon, lat)`, а `geom.y` — широта.
- Точка отеля — `representative_point` контура его здания, то есть расчёт идёт
  изнутри дома, а не из угла way.
- Обрезка области: `CLIP_BOUNDS = (20.40, 54.65, 20.85, 55.15)` — запад, юг,
  восток, север.
- Объекты вокруг отелей берутся в радиусе `OSM_RADIUS_M = 2200` м.

Почему не Overpass API:

- публичные зеркала отдают 429/502 под нагрузкой;
- часть зеркал — региональные экстракты и **молча возвращают пустоту**;
- расчёт перестал бы быть воспроизводимым.

Поэтому официальный экстракт Geofabrik один раз скачивается и обрезается локально.

Почему PBF, а не только shapefile: shapefile-выгрузка Geofabrik **теряет теги**
`building:levels` и `height`. Без них луч заката сравнивал бы этаж с константой
9 м. PBF читается `pyosmium`, замкнутые way и отношения-мультиполигоны
собираются в один слой, высота = `building:levels × 3 м` либо `height`.

Ограничение точности (важно для вопросов жюри): этажность известна у 53% зданий.
Остальным подставляется 9 м, и в `raw_evidence` пишется
`buildings_with_known_height` и `building_height_source` — по ним видно, посчитан
вид по реальной застройке или по константе. Это честнее, чем молча выдать
красивый результат.

## 6. Реестр характеристик — единственная точка расширения

`backend/app/features.yaml` описывает характеристики данными. Граф и поиск
читают его при старте, поэтому списка характеристик в Python нет.

Поля записи:

| Поле | Что задаёт | Влияет на |
| --- | --- | --- |
| `title`, `description` | человекочитаемое имя и смысл | UI, промпт LLM |
| `target` | `hotel` или `room` | планирование (номерные всегда через отельера) |
| `value_type` | `boolean` или `number` | приведение ответа отельера (`coerce`) |
| `value_field` | поле значения для сравнения | поиск, детекция противоречий, сравнение в UI |
| `ttl_days` | срок актуальности | `expires_at`, очередь перепроверки |
| `min_confidence` | порог «достаточно уверены» | решает, спрашивать ли отельера |
| `tools` | имена инструментов из `collectors.TOOL_REGISTRY` | что запускать; пусто → значение от отельера или из внешнего ingest |
| `question` | что спросить у отельера | если пусто, вопрос не задаётся никогда |
| `search.op`, `search.hint`, `search.min/max` | как трактовать пожелание и границы порога | разбор запроса |
| `authoritative` | кому верим при расхождении: `geo`, `hotelier`, `blogger` | `resolve_rows` |

Как добавить характеристику (без правки графа и поиска):

1. Блок в `features.yaml`.
2. Если нужен расчёт — функция в `app/tools/` и регистрация в `TOOL_REGISTRY`
   плюс каноническое имя источника в `TOOL_SOURCES`.
3. Если ответ приходит извне — ветка в `source_kind` при новом типе источника.

Три пути поставки значения (их важно не путать):

| Путь | Признак в реестре | Что делает агент |
| --- | --- | --- |
| Инструмент | `tools: [имя]` | запускает расчёт в узле `collect` |
| Ответ отельера | `tools: []` + непустой `question` | задаёт вопрос в `ask`, разбирает ответ в `parse` |
| Внешний ingest | `tools: []` + `question: ""` | не собирает ничего: значение приходит извне (партнёрские обзоры) |

Третий путь помечается в `tool_selection` и в логе прогона как «значение
приходит из внешнего источника», а не как «спросим отельера»: иначе на защите
возникает резонный вопрос, зачем отельеру вопрос про городскую смотровую
площадку. Если не задействован ни один из трёх путей, характеристика
существует в реестре и участвует в поиске, но значения у неё не будет —
в выдаче честное «нет данных», а не выдуманное число.

Проверено тестом: новая запись попадает в `GET /api/features`, участвует в
планировании и в разборе пожелания без изменений в Python-коде графа.

## 7. Агентный граф

Реализация — LangGraph (`backend/app/agents/graph.py`). Узлы:

| Узел | Что делает | Ключевое решение |
| --- | --- | --- |
| `plan` | составляет список характеристик и доступных инструментов | обоснование выбора пишется в `tool_selection` — видно в API и UI |
| `collect` | запускает инструменты | берёт лучший результат по уверенности, останавливается при достижении порога |
| `save` | пишет результаты **до** вопроса отельеру | чтобы собранное не потерялось, если ответа не будет |
| `conflicts` | ищет расхождения и решает, кого спросить | вопрос задаётся, если уверенность ниже порога, источники расходятся или пригодного свежего значения нет |
| `ask` | сохраняет вопросы в БД | очередь `pending` пересоздаётся, чтобы не копились дубли |
| `wait` | `interrupt()` — граф останавливается | состояние уходит в Postgres-checkpointer |
| `parse` | разбирает свободный ответ в значение | LLM (или мок) + приведение к типу реестра |
| `finalize` | записывает всё с `source`, `confidence`, TTL | одна строка на источник через `upsert_feature` |

Ветвление: из `conflicts` — либо в `ask` (если есть вопросы), либо сразу в
`finalize`. Номерные характеристики (`room_*`) и `pet_friendly` не имеют
инструментов, поэтому всегда уходят в вопрос.

Почему checkpointer в Postgres: с `MemorySaver` состояние живёт в памяти
процесса, и после `docker compose restart` незавершённый прогон терялся вместе с
`thread_id` — ответ отельера некуда было применить. Проверено фактом: прогон
остановился на `interrupt`, контейнер перезапустили, состояние прочиталось из БД
с теми же вопросами (`docs/HANDOFF.md`, §12 п.5).

Важное следствие архитектуры: **ответ отельера пишется напрямую**
(`routers/hotelier.py`), а не через возобновление графа. Причина описана в коде:
`ainvoke` по потоку, чьё состояние не подхватилось, запускает полный прогон
заново, `ask` пересоздаёт очередь вопросов с новыми `id`, и ответы на остальные
вопросы начинают отдавать 404. Ответ — самостоятельный источник, поэтому он
пишется тем же `upsert_feature`, что и граф.

Идемпотентность: `upsert_feature` удаляет строку того же источника и вставляет
новую. Повторный сбор не плодит дубли, а «нет данных» корректно затирает
устаревшее число от того же инструмента.

## 8. Модель достоверности — главная идея проекта

Требование ТЗ: «у каждого значения есть источник, уверенность и дата получения;
если источники противоречат, система это замечает и разбирается».

Реализация — поля таблицы `hotel_features`:

| Поле | Смысл |
| --- | --- |
| `source` | `SRTM+OSM`, `OSM`, `Open-Meteo`, `hotelier`, `blogger:<partner>` |
| `confidence` | уверенность от 0 до 1 (0.85 = 85%); чем измеряется — зависит от источника (см. раздел 9) |
| `raw_evidence` | доказательства: параметры расчёта, промежуточные значения, цитаты обзоров |
| `computed_at`, `expires_at` | когда получено и когда считается устаревшим |
| `disputed`, `disputed_with` | расхождение источников и все варианты |

Три правила, на которых держится вся конструкция:

**1. Одна строка на (отель, характеристика, источник).** Разные источники
сосуществуют: геоданные и ответ отельера не перетирают друг друга, поэтому
расхождение можно обнаружить. Инвариант поддерживается `upsert_feature` и
идемпотентной чисткой в `ensure_schema`.

**2. Авторитетный источник зависит от природы характеристики.** Функция
`resolve_rows` сравнивает `source_kind(source)` с `spec.authoritative`:

- измеримое (закат, шум, маршрут) → верим расчёту;
- субъективное (питомцы, сторона номеров) → верим отельеру;
- «эмоции» от мест → верим партнёрским обзорам со ссылкой и цитатой.

При равенстве решает уверенность, затем свежесть. Строки-заглушки
`{"status": "no_data"}` не участвуют в выборе, пока есть хоть один реальный факт —
иначе заглушка перебивала бы вычисленное значение.

**3. Расхождение не скрывается.** При записи значения `upsert_feature` сравнивает
`value_field` всех источников; если вариантов больше одного, все строки получают
`disputed=True` и снапшот вариантов в `disputed_with`. Дальше это видно в трёх
местах: в поиске («источники расходятся» в объяснении), в карточке отеля и в
кабинете отельера (`GET /api/conflicts` → `POST /api/hotelier/{id}/resolve/{key}`).

Почему уверенность считает наш сервис, а не поставщик данных: иначе появляется
второй источник истины, и на вопрос «почему вы уверены на 0.9» ответить нечем.
Поставщик даёт доказательства (цитату, ссылку, параметры), уверенность выводим мы
по прозрачной формуле.

Почему `source_kind` — отдельная функция с комментарием-предупреждением: если
добавить характеристику с `authoritative: blogger`, но забыть ветку в
`source_kind`, авторитетность молча станет нулевой, и расчёт будет перебивать
факт, подтверждённый обзорами. Это покрыто тестом
(`test_blogger_source_wins_where_it_is_authoritative`).

## 9. Алгоритмы

### 9.1 `sunset_view` — вид на закат (`app/tools/sunset_view.py`)

Константы: `RAY_LENGTH_M = 10 000`, `SAMPLE_STEP_M = 30`, `FLOOR_HEIGHT_M = 3`,
`DEFAULT_BUILDING_HEIGHT_M = 9`, `FACADE_TOLERANCE_DEG = 90`, проверяемые месяцы
`[4, 5, 6, 7, 8]`.

Шаги:

1. **Азимут заката на каждый месяц.** `pysolar.get_azimuth` для 21-го числа,
   18:00 UTC. Сезон важен: зимой закат юго-западнее, летом северо-западнее.
2. **Сторона окон.** Берутся направления наружных стен здания из контура OSM
   (`facade.building_wall_azimuths`). Месяц засчитывается, если хотя бы одна
   стена смотрит в сторону заката (в пределах 90°). Если контура нет —
   используется оценка по направлению на ближайшую улицу, и это помечается в
   `evidence.facade_model`; уверенность при этом умножается на 0.9.
3. **Луч** от точки отеля в сторону азимута длиной 10 км (`build_ray`).
4. **Рельеф.** Вдоль луча с шагом 30 м сэмплируется DEM. Линия визирования идёт
   к реальному горизонту: `d ≈ 3570·√h` метров. Это принципиальный момент —
   если считать визирование к высоте 0 на фиксированных 10 км, дальний рельеф
   ложно «перекрывает» вид с любого этажа.
5. **Застройка.** Здания, пересекающие луч (буфер ≈5 м), проверяются по высоте;
   здание самого отеля исключается — иначе оно затеняло бы вид из собственного
   окна.
6. **Перебор этажей** от 1 до `floors`: минимальный этаж, с которого открыт и
   рельеф, и застройка. Высота наблюдателя = абсолютная высота площадки из DEM +
   этаж × 3 м.
7. **Доля фасада** `west_share` — какая часть длины стен обращена к закату
   (0.25 = «западная стена из четырёх»). Это отвечает на вопрос «из какой части
   номеров видно», а не только «видно ли вообще».

Результат: `{visible, from_floor, months, azimuth_deg, west_share, confidence,
evidence}`. `confidence`: 0.2 без DEM, 0.45 без зданий, 0.7 при >50 зданиях в
буфере, 0.8 иначе; ×0.9 если направление окон неизвестно.

`block_reason` различает две причины отказа: `facade_facing_away` (окна не туда)
и `obstructed` (вид загорожен). Это не косметика: гостю в первом случае нужен
номер на другой стороне, во втором — этаж повыше.

Известный компромисс: закат «над морем» проверяется как открытый горизонт на
западе, а не как пересечение луча с водой. Море на западе в этом регионе есть,
поэтому для демо-региона различие несущественно, но в общем случае это
допущение (см. раздел 16).

### 9.2 `noise_score` — шум 0–100 (`app/tools/noise_score.py`)

Модель намеренно простая и объяснимая: сумма вкладов источников с линейным
затуханием внутри радиуса.

| Тег OSM | Вес | Радиус |
| --- | --- | --- |
| `highway=motorway`, `trunk` | 10 | 200 м |
| `highway=primary`, `secondary` | 6 | 150 м |
| `highway=residential` | 2 | 100 м |
| `railway=rail` | 7 | 300 м |
| `amenity=bar` | 8 | 150 м |
| `amenity=nightclub` | 10 | 200 м |

Вклад объекта: `weight × (1 − d / radius)`, то есть объект у самого отеля весит
максимум. Итог обрезается до 100. Уровни: <25 «Тихо», <55 «Умеренно», иначе
«Шумно». Уверенность 0.85 при трёх и более типах источников, иначе 0.7.

Ключевое: если рядом ничего не найдено, возвращается `score: None` и
`confidence: 0`, а не 0 баллов. Ноль без данных означал бы «идеальная тишина» —
это была бы выдумка, а не факт.

### 9.3 `walk_to_sea` — пешая доступность (`app/tools/walk_to_sea.py`)

1. Из слоя воды берутся **только пляжи** (`kind == "beach"`): река в центре
   города не делает отель «у моря».
2. Строится граф пеших связей из линий дорог; дороги класса
   `motorway/trunk (+_link)` исключены — по ним нельзя идти.
3. Старт и финиш привязываются к ближайшим узлам графа, путь ищется
   `networkx.shortest_path` по длине.
4. Скорость `WALK_SPEED_M_MIN = 80` м/мин, плюс штраф за подъём: 1 минута на
   каждые 10 м набора высоты по DEM.
5. Отдельно отмечается `crosses_highway` — есть ли на пути магистраль.
6. Отсечки: если прямая до пляжа > 3000 м или путь > 60 минут, возвращается «нет
   данных» с причиной. Это защита от разрывов в дорожной сети: правдоподобное
   «45 минут» вместо «сети нет» вводило бы гостя в заблуждение.

Уверенность 0.85. В `evidence` пишутся `straight_line_m`, `detour_ratio`,
`path_nodes`, `elevation_penalty_min`, `graph_nodes` — по ним видно, был ли путь
прямым или обходным.

## 10. Остальные источники

### 10.1 `climate_summer` (`app/collectors.py`)

Запрос к архиву Open-Meteo (ERA5) за 2019–2024, средний суточный максимум в
июле. Три попытки с паузой: сервис ограничивает частоту, а пакетный сбор идёт по
12 отелям подряд. Уверенность 0.85. При сбое возвращается `confidence: 0` и
`evidence.error`, причём **имя источника не меняется** между успехом и ошибкой:
иначе «нет данных» не затрёт прошлое значение, и в БД появятся две строки,
которые выглядят как расхождение источников.

### 10.2 `pet_friendly` и `room_*` — только отельер

Инструментов нет: из открытых данных это не выводится. Агент формулирует вопрос
из реестра, отельер отвечает свободным текстом.

Ответ приводится к типу характеристики функцией `FeatureSpec.coerce`:

- **boolean.** Модель охотно возвращает перечисление категорий («Люкс и
  Апартаменты») вместо «да». Без приведения в поиске оказалось бы
  `balcony: "Люкс и Апартаменты"`, и запрос «с балконом» перестал бы находить
  отель. Логика: явное «да/есть/можно» в начале → `True`, «нет/не/отсутств» →
  `False`, иначе проверка на отрицательные маркеры во всём тексте.
- **number.** Запятая как десятичный разделитель, нечисловое значение остаётся
  как есть (лучше строка, чем выдуманное число).

Значение хранится вместе с категорией номера, чтобы ответ «только люкс на 5
этаже» не превращался в «во всех номерах».

### 10.3 `sunset_spot_nearby` — партнёрский слой

Полное описание контракта — `data/guides/CONTRACT.md`. Здесь — суть обработки.

1. **Приём и валидация** (`app/guides.py`). Обязательны: ссылка, автор, дата
   публикации, цитата, координаты места, устойчивый `place.key`. Без цитаты факт
   отклоняется: «обзор так сказал» без ссылки неотличимо от выдумки модели.
2. **Склейка по месту.** Несколько обзоров об одной точке дают одно
   подтверждение, но считается число **независимых авторов**: перепечатка одного
   текста — не второе подтверждение.
3. **Уверенность:** `0.45 + 0.15 × min(авторов, 3) + 0.05` за подтверждение в
   OSM, потолок 0.95. Один обзор — 0.65, два — 0.75…0.80, три — 0.95.
4. **Привязка к отелям** (`scripts/ingest_guides.py`): отели в радиусе
   `MAX_STRAIGHT_M = 1500` м, маршрут считается тем же пешим графом, что и до
   пляжа. «Рядом» — не дальше 20 минут пешком.
5. **Запись:** `source = "blogger:<partner_id>"`, в `raw_evidence` — партнёр,
   лицензия, и по каждому обзору автор, ссылка, дата, цитата и локатор.

Почему ingest офлайн (`make guides`), а не запрос к партнёру в рантайме: демо
обязано подниматься одной командой `docker compose up --build` и не зависеть от
доступности чужого сервиса. Свежий снапшот забирается отдельной командой
`make guides-fetch`.

## 11. Поиск: от свободного текста до ранжирования

`backend/app/search_engine.py`, эндпоинт `POST /api/search`.

**Шаг 1. Разбор пожелания.** `parse_intent` даёт словарь
`{характеристика: порог}` и источник разбора.

- Если LLM доступен (`USE_MOCK_LLM=0` и есть ключ) — модель получает список
  характеристик **из реестра** вместе с `search.hint` и возвращает JSON.
- Если нет — работает детерминированный разбор по ключевым словам
  (`KEYWORD_INTENT`). Это не заглушка, а рабочий режим: демо обязано работать
  без ключа.
- Результаты объединяются: LLM уточняет эвристику, но не отменяет её.

**Шаг 2. Ограничение порогов.** `clamp` держит порог в границах из реестра.
Пример: модель охотно отвечает «шум 0» на просьбу «тихо», но шума 0/100 не
бывает — такой порог отсекает все отели. В реестре стоит `min: 10`.

**Шаг 3. Выбор значения среди источников.** Для каждого отеля строки
группируются по характеристике и прогоняются через `resolve_rows` — по правилам
раздела 8, а не «кто последний записал».

**Шаг 4. Скоринг.** `score = совпало / (совпало + не совпало + нет данных)`.
Сортировка: по `score`, затем по числу совпадений, затем по числу «нет данных»
(меньше — лучше). Смысл: отель, у которого известны все запрошенные
характеристики и все подходят, выше отеля с одной подходящей и тремя неизвестными.

**Шаг 5. Объяснение.** Строка собирается из сохранённого значения, источника и
уверенности. Примеры реальных формулировок: «закат виден с 4 этажа (SRTM+OSM,
уверенность 80%)», «шум 32/100 (Тихо) (OSM, уверенность 85%)», «закат в 3 мин
пешком, подтверждений: 2 (blogger:local-guides, уверенность 75%)». Если значение
не подошло — добавляется «— не то, что просили»; если источники расходятся —
«источники расходятся».

**Гейтинг партнёрской характеристики.** `sunset_spot_nearby` участвует в
ранжировании только тогда, когда попала в разобранный запрос. Запрос «хочу
встретить закат на берегу моря» её содержит; запрос «тихий номер у моря» — нет,
и тогда отель ранжируется как раньше, а место остаётся справкой в карточке.
В мок-режиме это обеспечено «иглами» про место, а не про закат вообще
(`закат на берег`, `закат у мор`, `смотров`, `закатн`) — иначе эмоция
подмешивалась бы в каждый запрос со словом «закат».

**Пустая выдача объясняется по-разному:** «пожелание не распознано» и
«характеристики ещё не собраны» — разные ситуации с разными действиями
пользователя.

## 12. API

Префикс `/api`, проксируется nginx. Авторизации в прототипе нет.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | healthcheck |
| POST | `/api/search` | поиск по описанию: `{query, limit}` |
| POST | `/api/search/intent` | только разбор запроса (отладка) |
| GET | `/api/hotels` | все отели с характеристиками и флагами `stale`/`disputed` |
| GET | `/api/hotels/{id}/features` | характеристики одного отеля |
| POST | `/api/hotels/{id}/enrich` | запуск агентного сбора (в фоне) |
| POST | `/api/hotels/enrich-all?limit=N` | сбор для всех отелей |
| GET | `/api/hotels/stale` | характеристики с истёкшим TTL |
| POST | `/api/hotels/{id}/refresh` | перепроверка отеля, возвращает список устаревших |
| GET | `/api/features` | реестр характеристик |
| GET | `/api/conflicts` | расхождения источников и выбранное значение |
| GET | `/api/agent/{thread_id}/stream` | SSE-поток шагов графа |
| GET | `/api/hotelier/inbox?status=all` | вопросы и история ответов |
| POST | `/api/hotelier/{hotel_id}/answer/{question_id}` | ответ отельера |
| POST | `/api/hotelier/{hotel_id}/resolve/{feature}` | подтвердить/исправить значение |
| GET | `/api/routes`, `/api/routes/{id}` | витрина маршрутов |

Пример поиска:

```bash
curl -s -X POST http://localhost:8080/api/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"хочу встретить закат на берегу моря и чтобы было тихо"}' \
  | python -m json.tool
```

Ответ содержит `intent` (что распознали), `intent_source` (`llm` или
`keywords`), `agent_log` (шаги) и `hotels` с полями `score`, `explanation` и
`features`.

## 13. Интерфейс

| Страница | Что показывает | Источник данных |
| --- | --- | --- |
| `/` | витрина маршрутов | демо-массив в `src/data/mockHotels.ts` (таблица `routes` в БД пуста — см. раздел 16) |
| `/search` | строка запроса, карта с лучами заката, карточки с объяснением | `POST /api/search` |
| `/hotel/:id` | все характеристики с confidence и evidence, блоки «устарело» и «источники расходятся», ответы отельера | `GET /api/hotels` |
| `/hotelier` | вопросы, история ответов с реальным `confidence`, разбор противоречий, очередь перепроверки | `/api/hotelier/*`, `/api/conflicts`, `/api/hotels/stale` |
| `/compare` | таблица 2–3 отелей с подсветкой победителя | реестр + значения |

Два решения, которые стоит знать при защите:

- **Откат на демо-набор.** Если бэкенд недоступен, интерфейс не ломается: стор
  переходит на `src/data/mockHotels.ts` и показывает плашку `демо-набор`.
  Пока источник не определён (`dataSource === 'unknown'`), список отелей пуст —
  иначе на холодном старте выдуманные отели успевали мелькнуть на экране.
- **Описание из мок-набора не подставляется.** `adapters.mapHotel` оставляет
  `description` пустым: текст из демо-данных утверждал факты и конкурировал с
  расчётом (у «Принцессы Элизы» описание гласило «фасад обращён на запад», хотя
  `sunset_view` даёт `facade_facing_away`).

Карта (`src/components/Map.tsx`) — MapLibre GL, тайлы OpenStreetMap, лучи
заката рисуются от отеля по `azimuth_deg`: оранжевый — виден, серый — нет.
Воркер MapLibre подключается через `?url`, потому что в бандле Vite его нет;
nginx отдаёт `.mjs` с правильным MIME-типом (иначе браузер отказывается создавать
module worker — это была реальная поломка, см. HANDOFF §12).

## 15. Метрики: что и как измеряется

`make eval` (`scripts/evaluate.py`) — три группы метрик.

**1. Покрытие и «сколько данных нет».** Считается всегда, разметки не требует.
Факт на демо-наборе: 96 строк характеристик, из них часть — «нет данных»;
`walk_to_sea` есть у 8 из 12 (у остальных пляжа в радиусе нет, и придумывать
значение мы не стали).

**2. Согласие с независимым baseline.** Для каждой гео-характеристики считается
грубая альтернатива **другим способом**:

| Характеристика | Baseline | Результат |
| --- | --- | --- |
| `walk_to_sea` | прямая до пляжа × 1.3 / 80 м/мин | MAE 4.8 мин (n=8) |
| `sunset_view` | только DEM, без зданий и без этажей | 8/12 совпадений, все 4 расхождения объяснены застройкой (2–17 зданий на луче), ложноположительных 0 |
| `noise_score` | плотность источников в 400 м без весов | Спирмен +0.91 (n=11) |

Это baseline, а не истина: метрика ловит расхождение **в разы**, но не точность
до минуты или до балла. Так и написано в отчёте, чтобы число не читалось как
«точность 91%».

**3. Точность на ручной разметке.** `data/ground_truth.csv` — шаблон на 12
отелей с колонками `sunset_visible` (0/1), `sunset_from_floor`,
`noise_level` (low/medium/high), `walk_minutes_ref`. Пустые поля **не считаются**:
подставлять вместо них наши же значения значило бы измерять систему самой собой.
Сейчас колонки не заполнены, поэтому `accuracy` честно не приводится.

Отдельно считается **доля вопросов к отельеру**: 5 вопросов на 4 из 12 отелей
(33%) — это метрика «насколько система уверена в данных», требуемая ТЗ.

## 16. Сильные стороны

1. **Каждое значение проверяемо.** У любого числа есть источник, уверенность,
   дата, срок актуальности и evidence с параметрами расчёта. На вопрос «откуда
   вы это взяли» есть ответ в БД, а не в презентации.
2. **Геометрия вместо догадок.** Закат считается raycasting'ом по рельефу и
   зданиям, а не «вероятно, виден». Для ТЗ это принципиально: «агент, который
   просит LLM угадать» назван нерешением.
3. **Расширяемость на уровне данных.** Новая характеристика — блок YAML;
   проверено тестом, что она появляется в реестре, планировании и разборе
   запроса без правки Python.
4. **Расхождение источников видно и разрешимо.** `disputed` + `authoritative` +
   разбор в кабинете: система не выбирает молча «последнее записанное».
5. **Актуализация работает.** TTL у каждой характеристики, очередь
   `/api/hotels/stale`, кнопка перепроверки, которая перезапускает сбор.
6. **Демо не зависит от внешних сервисов.** Данные в репозитории, LLM опционален,
   `docker compose up --build` работает без ключа и без сети.
7. **Честные отказы.** Нет данных — возвращается `confidence: 0` и причина, а не
   правдоподобное число. Это выдержано в `noise_score`, `walk_to_sea`,
   `climate_summer` и в партнёрском слое.

## 17. Слабые стороны и ограничения (честно)

| Ограничение | Причина | Чем грозит |
| --- | --- | --- |
| `accuracy` не измерена | `ground_truth.csv` не заполнен | на вопрос «точность» отвечаем «согласие с baseline», а не accuracy |
| 12 отелей, один регион | осознанный выбор в пользу глубины | выводы статистически слабые, генерализация не проверена |
| Этажность известна у 53% зданий | неполнота OSM | остальным подставляется 9 м; помечено в evidence, но точность ниже |
| Закат = открытый горизонт на западе | упрощение модели | не проверяется именно пересечение луча с водой |
| Шум — линейная модель | упрощение | нет ночных карт шума, нет высоты источника и экранирования |
| Маршрут по дорогам без тротуаров | нет атрибутов пешеходной сети | минуты приблизительны, переход через магистраль отмечается по классу дороги |
| Партнёрский корпус демонстрационный | нет доступа к реальному сервису | ссылки ведут на `example.com`, `osm`-проверка места не выполняется |
| Главная страница показывает демо-маршруты | таблица `routes` в БД не заполняется | демо-данные выглядят как собранные — это надо либо добить, либо убрать |
| Нет авторизации | прототип | кабинет отельера открыт всем |
| Нет миграций Alembic | время | схема правится идемпотентными `ALTER` |
| SSE-эндпоинт не используется фронтом | шаги приходят в `agent_log` из `/search` | эндпоинт работает, но в UI не задействован |
| Конверсия не измеряется | вне возможностей прототипа | продуктовая гипотеза остаётся гипотезой |

## 18. Куда развивать

**P1 — закрывает вопросы, которые зададут первыми**

1. Заполнить `ground_truth.csv` по панорамам и отзывам → получить `accuracy` и
   вынести в README. Это первый вопрос любого жюри.
2. Проверять закат именно над водой: пересечение луча с полигоном моря, а не
   только открытый горизонт.
3. Интеграционные тесты: HTTP + БД (хотя бы один прогон «enrich → поиск →
   ответ отельера»).
4. Наполнить `routes` из партнёрских обзоров и убрать демо-массив с главной.
5. Авторизация кабинета отельера (хотя бы токен на отель).

**P2 — усиление продукта**

6. Второй регион, чтобы проверить генерализацию алгоритмов.
7. Ночные карты шума (для Европы есть открытые) вместо самодельной модели.
8. Время поездки по датам: `check_in/check_out` в запросе → фильтр по `months`
   у заката и эмоций, а не «в среднем за год».
9. Больше источников из ТЗ: GTFS (транспорт), OpenAQ (воздух), OpenCellID
   (связь), Wikidata (история здания) — реестр это позволяет, нужны инструменты.
10. `pgvector` для «похожих отелей»: расширение уже в стеке, но не используется.

**P3 — продуктовая зрелость**

11. Метрики конверсии в проде: CTR карточки, доля броней после запроса с
    эмоциями против обычного фильтра, влияние на отмены.
12. Кэш графа маршрутов и очередей перепроверки; стоимость LLM на запрос.

```bash
docker compose up -d --build
curl http://localhost:8080/health

# собрать характеристики для всех отелей (~2 минуты, фоновые задачи)

# что получилось по конкретному отелю
curl -s http://localhost:8080/api/hotels/13/features

curl -s -X POST http://localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query":"встретить закат на берегу моря"}'
curl -s -X POST http://localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query":"тихий номер у моря"}'

make guides   # партнёрские обзоры → характеристики
make eval     # покрытие и согласие с baseline
make test     # 50 юнит-тестов

# показать очередь перепроверки: состарить климат
docker compose exec -T db psql -U routely -d routely -c \
  "update hotel_features set expires_at = now() - interval '1 day' where feature_key = 'climate_summer';"
curl -s http://localhost:8080/api/hotels/stale
```
